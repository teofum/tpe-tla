This file has implementation notes worth keeping in mind for the final report.

- Tests involving external files (import expressions) are ignored because they
  break in CI.

- Tests involving multiple files (@import/@export) are ignored as the test
  runner can't start them in its current form.

- Default parameter eval is inefficient, we could cache them since they are by
  definition the same each time the function is called. Too bad!

- Typed CSV imports: to keep things reasonably simple, typecheck only checks the
  specified type is CSV-compatible, i.e., there exists some CSV that could
  fit the row type with coercion. It doesn't actually look through all the rows
  and attempt to coerce. This is done during eval, and produces an error there
  if it fails.

- Typed CSV imports: if the specified type is a union, the type checker picks
  the first CSV-compatible type and uses it for coercion hinting. This can cause
  a union that would accept the CSV to fail on eval, for example:

  import csv of union { int[string], string[string] } "records.csv"

  Because the first type int[string] is CSV compatible (as long as the fields
  can all be parsed to integers) it will be picked and eval will try to coerce
  the CSV to it; if it has non-integer fields it will fail.

  Ideally, we would use the *least restrictive* type in a union instead, but
  this is fairly hard to determine and we only have so much time on this earth.
  And, uh, until the deadline.

- Enums: removed from the spec, difficult to implement with structural typing
  and generally not very useful.

#=== Overall architecture plan ================================================#

The compiler will follow a sequence of steps; at the end of each an error gate
is ran and if any errors are detected, compilation will be halted. Warnings are
reported, but allow the compiler to continue.

1. Parsing [DONE]:
  Each input file is parsed into an AST using Flex+Bison. This step may produce
  syntax errors.

The following steps are executed in order, each for every file.

2. Static symbol pass [DONE]:
  The AST for the file is scanned for type and function definitions, and the
  type and function symbol tables are built, including scope information.

3. Type checking [DONE]:
  Once the static symbol table is built, all statements and expressions in the
  file are type checked. Function definitions are type checked at the end of
  their respective scope. The variable symbol table is also built during this
  step, as it's needed for type checking, and symbol reference integrity is
  also checked at this point.

These two stages may produce type errors and symbol errors (e.g., redefinition
of an already defined function or type, use of an undefined variable).

4. Evaluation [DONE]:
  The goal of this step is to reduce an AST (i.e., a program) to a single value
  or a list of values. Expressions are evaluated in order from top to bottom,
  and reduced to the value they return. Because symbol integrity has been
  validated during type checking, it can be assumed any symbols referenced at
  this stage are well defined.

The evaluation stage may produce evaluation errors. These are what most
languages would call runtime errors, e.g., a division by zero, an out of bounds
list index, or an import error.

MAYBE: cache the values produced by eval, to allow faster recompilation if some
files have errors? We can easily invalidate by source file modified timestamp.
NOTE: if we do this, need to also list any dependencies such as imports.

5. Code generation [DONE]:
  This step is run immediately after evaluation. The value or values produced
  are converted to an output file (html). This step shouldn't produce any errors
  as the results of the evaluation stage should be valid, but I/O errors may
  still happen.

#=== Parser ===================================================================#

Tuple literals and list literals are syntactically identical, so both are parsed
as list literals; there is no such thing as a tuple literal in the AST.
  - The backend should interpret list literals contextually: a heterogeneously
    typed literal is always a tuple; a homogeneous one can be either a tuple
    or a list.
  - For inference purposes, a homoegeneous list literal is always interpreted
    as a list; homogeneous tuples MUST be explicitly typed.

#=== Backend ==================================================================#

Function composition implementation ideas: lexical scope capture is hard, do
we actually need it? On a function call with a compose block:
  - The block is executed *before* the function call, within the caller's scope
  - The resulting value is passed to the function as a special parameter
  - The "compose" expression returns that value
This is simple to implement (no scope capture needed, as we don't defer
execution), works perfectly for our purposes, and allows using "compose" as part
of an expression:

  foo is function() -> string[] {
    [compose, "is", compose]
  }

In this example, "compose" is used multiple times, but only evaluated once: from
the callee's point of view, it's just a special parameter.
