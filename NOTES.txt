#=== Overall architecture plan ================================================#

The compiler will follow a sequence of steps; at the end of each an error gate
is ran and if any errors are detected, compilation will be halted. Warnings are
reported, but allow the compiler to continue.

1. Parsing [DONE]:
  Each input file is parsed into an AST using Flex+Bison. This step may produce
  syntax errors.

The following steps are executed in order for a given scope. After parsing,
these steps are run on the main (file) scope of each file.

2. Symbol pass [TODO]:
  The AST representing the scope is scanned (shallow) for type and function
  definitions and constants, and a symbol table is built. At the file scope,
  both per-file and global (export) symbol tables are built.

3. Type checking [TODO]:
  Once the local symbol table is built, all statements and expressions in the
  scope (shallow) are type checked. Note that this includes types and
  definitions already in the symbol table; we eagerly add them so they can be
  used in type checking regardless of where they were declared.

These two stages may produce type errors and symbol table errors (e.g.,
redefinition of an already defined variable, function or type). Once all files
have been checked, the next steps are run on each one:

4. Evaluation [TODO]:
  The goal of this step is to reduce an AST (i.e., a program) to a single value
  or a list of values. Expressions are evaluated in order from top to bottom,
  and reduced to the value they return. When a nested scope (block) is
  encountered as part of an expression, before it is evaluated, steps 2. and 3.
  are run on this nested scope. This is done even if the scope will not be
  evaluated, to report any errors in it.

Note that nested scopes are symbol-passed and typechecked lazily. This is done
for two reasons:
  - Symbols can't outlive their scope, so we can save resources by dropping the
    symbol table of a nested scope as soon as we're done evaluating it. If we
    eagerly built symbol tables for every scope, we'd have to store all of them
    for the entire duration of the evaluation phase.
  - Nested scopes can use symbols from their ancestor scopes, even ones defined
    later in the file (avoids the need for forward declarations), which requires
    we only look at a scope *after* building and typechecking the entire symbol
    table for all of its ancestors. The evaluation phase is a neat way to do so.
Any symbol table or type errors in a nested scope immediately halt evaluation of
its ancestor scopes, up to the file level, as their value cannot be obtained.
The compiler still attempts to evaluate any remaining files, for the purpose of
error checking and reporting.

Also note that the symbol table for a scope can be modified during evaluation:
variables are not added during the symbol pass, as they cannot be referenced
before they are defined, and their value may be altered by assignments.

The evaluation stage may produce evaluation errors. These are what most
languages would call runtime errors, e.g., a division by zero, an out of bounds
list index, or an import error.

MAYBE: cache the values produced by eval, to allow faster recompilation if some
files have errors? We can easily invalidate by source file modified timestamp.
NOTE: if we do this, need to also list any dependencies such as imports or
files we use exported symbols from.

5. Code generation [TODO]:
  This step is run immediately after evaluation. The value or values produced
  are converted to an output file (html). This step shouldn't produce any errors
  as the results of the evaluation stage should be valid, but I/O errors may
  still happen.

#=== Parser ===================================================================#

Tuple literals and list literals are syntactically identical, so both are parsed
as list literals; there is no such thing as a tuple literal in the AST.
  - The backend should interpret list literals contextually: a heterogeneously
    typed literal is always a tuple; a homogeneous one can be either a tuple
    or a list.
  - For inference purposes, a homoegeneous list literal is always interpreted
    as a list; homogeneous tuples MUST be explicitly typed.

#=== Backend ==================================================================#

Function composition implementation ideas: lexical scope capture is hard, do
we actually need it? On a function call with a compose block:
  - The block is executed *before* the function call, within the caller's scope
  - The resulting value is passed to the function as a special parameter
  - The "compose" expression returns that value
This is simple to implement (no scope capture needed, as we don't defer
execution), works perfectly for our purposes, and allows using "compose" as part
of an expression:

  foo is function() -> string[] {
    [compose, "is", compose]
  }

In this example, "compose" is used multiple times, but only evaluated once: from
the callee's point of view, it's just a special parameter.
